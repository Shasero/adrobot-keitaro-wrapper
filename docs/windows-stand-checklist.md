# TASK-008B. Чек-лист владельца стенда для Windows

Заполняется во время отдельного прогона. Для каждого пункта укажите «пройден», «блокер» или «не проверено», время и безопасное свидетельство. Исходная база аудита — TASK-007, коммит `5b079825b2e2bcfda1446f8939edc97f9047cb98`. Перед прогоном сверьте фактический SHA с версией, принятой владельцем для стенда, включая исправление TASK-008A после его приёмки.

## Локальный запуск

В новом каталоге PowerShell выполните команды из README. Для уже подготовленной копии начните с проверки SHA и сохраните существующий `.env` и SQLite.

```powershell
git clone --branch develop --single-branch https://github.com/Shasero/adrobot-keitaro-wrapper.git adrobot-008b
Set-Location adrobot-008b
git rev-parse HEAD
py -3.12 -m venv .venv
$python = ".\.venv\Scripts\python.exe"
& $python -m pip install -r requirements.txt
& $python -m pip check
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
& $python -m alembic upgrade head
& $python -m alembic current
& $python -m alembic check
& $python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

- [ ] Ожидаются ревизия 0003, согласованная схема и ответы 200 на `/`, `/health`, `/docs` и `/openapi.json`. Начните с пустого ключа и отдельной файловой БД. Ошибка при миграции или запуске — остановка до подключения стенда. Откат на рабочей БД не выполнять.
- [ ] Для отдельной проверки межпроцессной блокировки Windows остановите сервер или откройте второе окно PowerShell из того же каталога. Установите тестовые зависимости командой `& .\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt` и выполните `& .\.venv\Scripts\python.exe -m pytest -q tests/test_offer_editor.py::test_publication_excludes_other_process`. Ожидаются временная SQLite, моки, один PUT и блокировка конкурента. На Windows тест использует обычный путь к общей БД. При падении сохраните очищенное сообщение и отложите публикацию привязок.

## Проверки на выделенном стенде

| Шаг | Действие и ожидаемый результат |
| --- | --- |
| ☐ 1. Доступ на чтение | Настройте локально HTTPS-адрес Admin API с окончанием `/admin_api/v1`, ключ, префикс проекта и ID домена, группы кампаний и источника из README. Перезапустите приложение. Через разрешённый клиент проверьте GET доменов, групп кампаний, источников и офферов. Сверьте три ID и доступность нескольких активных офферов. В UI видны только кампании своего префикса и подходящие потоки. При неверном ID, чужой принадлежности или ошибке доступа остановитесь. |
| ☐ 2. Разрешение на запись | До первого POST получите явное разрешение владельца на одну новую изолированную тестовую кампанию с уникальным именем и согласованными GEO и офферами. Для проверки двух потоков используйте эту новую кампанию. Диагностическая кампания 89 уже содержит четыре потока. Чужие кампании, глобальные офферы, домены, группы и источники доступны только для чтения. |
| ☐ 3. Одно создание | Один раз нажмите «Создать кампанию». Запишите UUID, alias, известные ID и стадию. Ожидается `succeeded`. При обрыве, `running`, `partial`, `unknown` или 503 остановите записи, прочитайте статус того же UUID и сверьте объекты по alias и известным ID. Возобновление — только после решения владельца. |
| ☐ 4. Независимое чтение | По ID кампании прочитайте её параметры и список потоков, затем детали обоих потоков. Сверьте префикс, alias, домен, группу, источник, тип position, active, TTL 24, CPC/USD, `cost_auto=true` и `uniqueness_method=ip`. Ожидаются ровно два активных потока. Позиция 1 — regular/redirect, HTTP-переход в Google и единственный country/accept с выбранным GEO. Позиция 2 — default/landings без фильтров, один выбранный активный оффер 100%. Расхождение зафиксируйте до редактирования. |
| ☐ 5. Черновик и Cancel | В потоке 2 добавьте второй активный оффер, закрепите одну долю и добавьте третий. Проверьте неизменность закреплённой доли и сумму 100%. Удалите незакреплённую строку, проверьте 0%, затем Bring Back и Cancel. Сверьте с исходной базой. До Push удалённый состав сохраняется. |
| ☐ 6. Подготовка нескольких привязок | Снова добавьте офферы. Получите разрешение на Push указанного состава, выполните его один раз. Независимым GET проверьте полный непустой состав, ID, доли и остальные настройки потока. Это исходная точка следующего шага. |
| ☐ 7. Удаление одной привязки | Из опубликованных нескольких строк удалите одну, оставив хотя бы одну активную. После согласованного Push выполните независимый GET. Удалённый ID отсутствует в составе, остальные ID офферов и сумма 100% сохранены. Сравните ID сохранившихся привязок и поля потока до/после: кампанию, тип, схему, состояние, позицию, действие, фильтры и лендинги. В AdRobot удалённая строка остаётся с 0%. При неподтверждённом результате остановите записи и выполните Refresh. |
| ☐ 8. Внешнее изменение | Только по отдельному разрешению через Keitaro измените привязки в этом же тестовом потоке, оставив корректный непустой состав. С чистым черновиком Refresh должен показать `external_removed` и 0%. Для отдельно согласованного повтора с локальными правками ожидайте конфликт и сохранённый черновик. Cancel → Refresh принимает внешний состав. Глобальный объект оффера не удаляется. |
| ☐ 9. Проверка маршрутизации | Только если эмулятор поддерживает клики и документирован способ задать страну, проверьте тестовый переход для выбранного и другого GEO. Ожидаются Google и замыкающий оффер соответственно. Без достоверного способа задать GEO отметьте «фактический переход не проверен», отдельно сохраните результат чтения конфигурации. Произвольный HTTP-заголовок, реальный рекламный трафик и конверсии в этот сценарий не входят. |
| ☐ 10. Завершение | Если локально удалены все строки, сумма 0%, Push заблокирован. Очистку landings можно вынести в отдельный эксперимент со своим потоком, снимком исходного состава, планом восстановления и отдельным разрешением владельца. Опыт с пустым redirect относится только к redirect. Остановите локальный сервер Ctrl+C. Оставьте удалённые объекты для ревью, без автоматического cleanup. |

При конфликте ревизии перечитайте черновик. При неопределённом PUT используйте явную сверку. Наблюдение исходной базы в момент GET допускает позднюю запись. Перед новой попыткой вручную проверьте актуальные привязки и подтвердите это в UI. Между GET и PUT возможна внешняя запись. Web Locks координирует вкладки одного origin и профиля браузера.

Для отчёта достаточно SHA, версии Windows и браузера, времени, стадии, безопасных ID тестовых объектов, списка долей до/после и очищенных снимков UI. Закройте секреты, адреса переходов, приватные имена и данные трекера. Не прикладывайте .env, полные ответы, заголовки, сетевые трассы и токены. Ошибку фиксируйте безопасным кодом, шагом и ожидаемым результатом.
