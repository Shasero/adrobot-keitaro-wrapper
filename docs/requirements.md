# Требования к AdRobot

## Требования задания

### Создатель кампаний

- Ввод принимает название кампании, GEO-код страны и ID оффера. В примере интерфейса показан поиск офферов с автодополнением.
- Имя кампании начинается с `test_<surname>_`. Кампании назначаются домен, группа и источник трафика. Используется ротация по позиции.
- Первый, обычный поток фильтрует по выбранной стране и ведёт на Google. Второй, замыкающий поток работает без фильтра и ведёт на выбранный оффер с долей 100%.

### Редактор кампаний

- Редактор существующих кампаний позволяет искать, добавлять и удалять привязки офферов к потоку и показывает их корректные доли.
- Изменения остаются черновиком до **Push to KT**. **Cancel** отменяет изменения черновика.
- Удалённый оффер отображается с долей 0%. Действие **Bring Back** возвращает привязку. Долю можно закрепить (**pin**).
- При синхронизации редактор обнаруживает, что оффер был удалён из потока извне. Перечисленные сценарии редактора зафиксированы по анализу демонстрации.

### Стек и поставка

- Обязательны FastAPI и SQLAlchemy. Технологии фронтенда выбирает проект.
- Репозиторий GitHub публичный. README объясняет, как применить миграции и запустить приложение. Скринкаст длительностью до трёх минут необязателен.

## Предлагаемые инженерные решения и критерии

- Хранить черновики, закрепления, удалённые привязки и базовый снимок опубликованного состояния в SQLite. Для схемы использовать Alembic. Keitaro остаётся источником фактического опубликованного состояния.
- Использовать целые проценты. Активным незакреплённым офферам распределять оставшуюся после закреплённых долей часть максимально равномерно. При наличии остатка выдавать по одному процентному пункту в детерминированном порядке. Для трёх незакреплённых офферов это даёт 34/33/33. Сумма долей при наличии активных офферов должна быть 100%, при их отсутствии — 0%. Закреплённые значения сохранять. Невозможную конфигурацию отклонять с понятной ошибкой. Правила граничных случаев и порядок распределения остатка согласовать до реализации.
- Для поиска достаточно названия или ID. GEO относится к переходу на Google в первом потоке. Отдельный фильтр по GEO оффера возможен после согласования.
- Перед публикацией сравнивать актуальный снимок Keitaro с базовым снимком черновика. При конфликте сообщать о расхождении и останавливать публикацию. После записи через GET проверять привязки и остальные поля потока. **Cancel** возвращает черновик к опубликованному состоянию без PUT.
- Создание кампании состоит из нескольких HTTP-запросов. Транзакция SQLite охватывает только локальные данные. При частичном сбое сообщать о фактическом результате каждого шага. Перед повтором POST установить, был ли объект создан. Стратегию восстановления или компенсации согласовать при реализации. Автоматическое удаление реальных объектов требует согласованной политики.
- Интерфейс и README должны позволить проверяющему запустить приложение и пройти сценарии без личных секретов автора.

### Правила редактора TASK-006

Одна версия черновика относится к паре из удалённых ID кампании и потока.
Каждая запись проверяет expected_revision атомарно. Источник опубликованных
долей — контрольное чтение Keitaro. Импорт, refresh и pin сохраняют исходные
доли. После изменения состава или unpin целый остаток выдаётся по возрастанию
ID среди незакреплённых строк. Каждая активная строка получает положительную
долю. Удаление снимает закрепление и сохраняет строку с 0% для Bring Back.

Изменения закреплений сохраняются между запусками. Push одних метаданных
принимает их локально. При конфликте черновик и база сохраняются до решения
оператора. Cancel, затем refresh принимает внешний состав с отметками об
удалённых строках. При неопределённом результате PUT применяется явная сверка
с целью и базой, включая отпечаток остальных полей. Проверки автоматизированы
на MockTransport. Живая проверка удаления привязок в landings относится к TASK-008.
