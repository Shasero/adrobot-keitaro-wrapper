# AdRobot

AdRobot — проект создателя кампаний и редактора привязок офферов для Keitaro.
Приложение на FastAPI, SQLAlchemy и SQLite включает веб-интерфейс и HTTP API
создания кампаний, поиска и редактирования привязок офферов.
Для запуска приложения и миграций ключ не требуется.

Для интеграции задайте на сервере `KEITARO_BASE_URL` с HTTPS и путём
`/admin_api/v1`, `KEITARO_API_KEY` и префикс проекта `CAMPAIGN_NAME_PREFIX`.
Клиент проверяет настройки при создании и поддерживает контекстный менеджер.
Ответы могут содержать чувствительные поля и предназначены для внутренней обработки.
Тесты клиента используют HTTPX MockTransport. Запросы к реальному API не выполнялись.

## Локальный запуск

Нужен Python 3.12. Выполняйте команды из корня репозитория. Копируйте шаблон
настроек только при первом запуске. Храните секреты в переменных окружения
или локальном `.env` и не публикуйте ключи. Переменные окружения имеют
приоритет над `.env`, который читается как UTF-8.

### Windows PowerShell

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
alembic upgrade head
python -m uvicorn app.main:app --reload
```

Если PowerShell блокирует активацию, вызывайте
`.\.venv\Scripts\python.exe` напрямую с `-m pip`, `-m alembic`,
`-m uvicorn` или `-m pytest`.

### Linux и macOS

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
test -e .env || cp -n .env.example .env
alembic upgrade head
python -m uvicorn app.main:app --reload
```

- Стартовая страница — http://127.0.0.1:8000/
- Liveness — http://127.0.0.1:8000/health
- Документация OpenAPI — http://127.0.0.1:8000/docs

`/health` проверяет, что HTTP-приложение отвечает. `/docs` показывает схему
OpenAPI локально и содержит ссылку на `/openapi.json`.

## База данных

Приложение и Alembic используют `DATABASE_URL`. Стандартный путь
`sqlite:///./adrobot.db` разрешается относительно рабочей директории.
Поддерживается только SQLite: межпроцессная блокировка публикации редактора
реализована локальным файлом рядом с базой. PostgreSQL и MySQL пока не
поддерживаются. Для публикации используйте файловую базу SQLite; режим
`:memory:` для публикации не подходит.
Применяйте миграции командой `alembic upgrade head`. Сохраняйте существующую
базу при повторном запуске. Откат первой миграции удаляет таблицу
`managed_campaigns` вместе с её данными.

Таблица `managed_campaigns` учитывает операции AdRobot. `created_at` и
`updated_at` при вставке заполняет SQLite через `CURRENT_TIMESTAMP` с
точностью до секунды. Python получает значения UTC без смещения часового
пояса. SQLAlchemy обновляет `updated_at` при записи через модель, если
значение не задано явно. Для прямого SQL автоматического обновления нет.

## API создания кампаний

Запускайте приложение локально. Для создания также задайте положительные
`KEITARO_DOMAIN_ID`, `KEITARO_GROUP_ID`, `KEITARO_TRAFFIC_SOURCE_ID`.
`GET /api/offers?q=example&limit=20` возвращает ID и имена активных офферов.
Поиск по части имени игнорирует регистр, по ID требуется точное совпадение.
По умолчанию возвращаются до 20 записей, допустимый limit — от 1 до 100.

Тело `POST /api/campaigns` (пример для локального мока):

```json
{"operation_id":"76abc041-adad-483a-ac6d-dab1e26b97d7","name":"Demo","geo":"us","offer_id":501}
```

Генерируйте UUID один раз на намерение создать кампанию. Пробелы по краям
имени удаляются. Предел имени с префиксом — 120 символов. GEO проверяется
по локальному списку ISO 3166-1 alpha-2. Alias содержит UUID операции.
Успех 201 означает, что конфигурация кампании и двух потоков подтверждена GET.
Проверки проводились на моках. Фактический переход и создание на живом стенде
не проверялись.

`GET /api/campaigns/operations/{operation_id}` возвращает локальный статус,
стадию, alias и известные ID. Повтор POST с тем же UUID и параметрами
возвращает сохранённый терминальный результат (200). Другие параметры или
уже выполняющаяся операция дают 409. Ошибки ввода дают 422, конфигурации и
локального хранения — 503, upstream — 502 или 504 при таймауте.

Операция `failed` завершилась до подтверждённого внешнего эффекта.
`partial` сохраняет известные ID, `unknown` означает неопределённый итог
последней записи. После аварии может остаться `running` с последней стадией.
При этих трёх состояниях сверьте alias и ID вручную перед новым UUID:
новый UUID может создать дубликат. При ошибке БД поле `observed_ids` может
содержать полученные от API идентификаторы, сохранение которых не подтверждено.
Автоматического возобновления и удаления объектов нет.

Ревизия 0002 добавляет журнал `campaign_operations`. При откате до 0001
удаляется журнал, включая UUID и информацию для защиты от повторов. Откат
проверяйте на временной базе. Существующие записи `managed_campaigns` сохраняются.

## Backend редактора офферов

Для выбора кампании используйте `GET /api/campaigns`, затем
`GET /api/campaigns/{campaign_id}/streams`. В список попадают кампании
настроенного префикса, включая созданные вручную. Редактор поддерживает потоки
`regular` и `default` со схемой `landings`. Поиск оффера выполняет существующий
`GET /api/offers`. Справочники и ответы фильтруются на сервере.

Пример локальной последовательности для кампании 1, потока 2 и оффера 20.
Путь редактора — `/api/campaigns/1/streams/2/editor`. Версию для каждого
следующего запроса берите из предыдущего ответа.

| Метод и путь относительно редактора | Тело | Результат |
| --- | --- | --- |
| GET самого редактора | — | Открывает черновик с текущей revision или создаёт его по удалённым привязкам |
| POST /actions | `{"expected_revision":1,"action":"add","offer_id":20}` | Изменяет локальные строки |
| POST /refresh | `{"expected_revision":2}` | Сверяет базу и каталог, показывает внешние изменения |
| POST /cancel | `{"expected_revision":3}` | Возвращает принятую базу с её закреплениями и удалёнными строками |
| POST /push | `{"expected_revision":4}` | Публикует полный активный состав и проверяет его отдельным GET |

Поддерживаются действия `add`, `remove`, `restore`, `pin`, `unpin`. При
импорте и refresh доли сохраняются. Pin закрепляет текущую долю. При изменении
состава и снятии закрепления остаток распределяется поровну, лишний процент
получают сначала меньшие ID. Например, 34/33/33 с закреплёнными 34% после
добавления четвёртой строки становится 34/22/22/22. Удаление снимает pin.
Повторный add активной строки ничего не меняет, add удалённой эквивалентен
restore. Удалённые строки хранятся с 0% и после Push. Новые и восстановленные
офферы должны быть активны в каталоге. Неподдерживаемые доли или состояния
исходных привязок требуют проверки оператором. Пустой черновик допустим,
публикация пустого состава заблокирована.

Ответ содержит строки, `revision`, `dirty` (изменились привязки),
`metadata_changed` (изменились локальные атрибуты строк), `status`, `stage`,
`error_code`, `outcome_unknown` и `changes` со списками ID. Отсутствующий в
каталоге оффер показывается по ID с `available=false`. Для чистого черновика
refresh сохраняет внешнее удаление как `external_removed` и снимает pin при
смене доли. При расхождении с локальными изменениями, включая неподтверждённые
pin, возвращается 409 с черновиком. Cancel и последующий refresh позволяют
явно принять внешнее состояние. Push одних закреплений сохраняет их локально.

Публикация использует условное обновление SQLite по revision и блокировку
операционной системы на пару кампания/поток. Служебные файлы рядом с файловой
SQLite-базой в `.adrobot-editor-locks` должны быть доступны всем локальным
процессам приложения. Дескриптор освобождается при завершении процесса.
Во время публикации сохраняются стадия и целевой состав. При 4xx с определённым
отказом черновик доступен для исправления. При 5xx, обрыве, таймауте или
непригодном ответе PUT статус становится `unknown`. При ошибке контрольного
GET или несовпадении полей — `verification_failed`. Сбой SQLite даёт 503:
достоверна только последняя зафиксированная стадия.

После аварии или неопределённого исхода вызовите refresh. Совпадение с целью и
отпечатком остальных полей подтверждает публикацию. Совпадение с базой даёт
`base_confirmed` и разрешает новую явную попытку с возвращённой revision.
Другое состояние оставляет `reconciliation_conflict` до ручной сверки.
Cancel при незавершённой публикации заблокирован. Ответы ошибок содержат
`code`, `message` и при наличии `editor`. Используются 403 для нарушенной
принадлежности, 404 для отсутствующего черновика, 409 для конфликтов версий
или блокировки, 422 для недопустимых действий, 502/504 для ошибок интеграции,
503 для локального хранения и настроек.

Подтверждённого механизма ETag/CAS Keitaro нет. Внешний редактор может записать
данные между последним GET и PUT. Сверка показывает состояние на момент GET.
Проверки TASK-006 выполнены на MockTransport. Непустая замена с исключением
одной привязки и очистка всех привязок landings остаются для TASK-008.
Откат миграции 0003 удаляет черновики, pins и сведения о незавершённых
публикациях. Проверяйте откат на временной БД.

## Работа через веб-интерфейс

Откройте главную страницу на `127.0.0.1`. Для работы с Keitaro настройте
`KEITARO_BASE_URL`, `KEITARO_API_KEY` и `CAMPAIGN_NAME_PREFIX` на сервере.
Для создания кампаний дополнительно нужны ID домена, группы и источника.

1. В «Создателе кампаний» введите название и GEO, найдите и явно выберите
   оффер. При обрыве нажмите «Проверить статус». Браузер хранит UUID и
   параметры операции, чтобы использовать их после перезагрузки. После
   неопределённого результата сверьте alias и известные ID перед выбором
   «Новая операция».
2. В «Редакторе офферов» выберите кампанию и поток. Добавление, удаление,
   закрепление и Bring Back сохраняют черновик на сервере. Push to KT
   публикует изменённые привязки, а изменения одних закреплений принимает
   локально. Cancel отменяет локальные правки.
3. Refresh сверяет черновик с Keitaro. При конфликте Cancel и следующий
   Refresh позволяют принять удалённое состояние. После обрыва запроса
   перечитайте черновик и затем выполните сверку.

Интерфейс рассчитан на локальный запуск. Публикация пустого состава
заблокирована до стендовой проверки. Проверки интерфейса используют
синтетические данные. Проверка удаления привязок в landings и фактических
переходов клика на стенде остаётся отдельной задачей.

Резервирование UUID и явный сброс используют Web Locks одного origin
в одном профиле браузера. Блокировка удерживается до ответа на создание.
Если Web Locks недоступен, создание и сброс отключены. Другой профиль или
браузер может создать отдельную операцию с тем же названием.

После неопределённого PUT чтение исходной базы сохраняет требование ручной
сверки в серверном черновике. Подтверждение оператора требуется при следующей
публикации изменённых привязок. Для прежних черновиков требование восстанавливается
по сохранённому коду `base_confirmed`. Если старая версия уже очистила код,
определить прежнее требование по документу невозможно.
